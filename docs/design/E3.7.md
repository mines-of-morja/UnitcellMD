# E3.7 design — OpenMM as GPU backend (as built)

- **Status:** implemented 2026-11-17 on engine branch `e37-openmm`. The author approved the
  research plan, with GPU-first throughput (decision D3). The decisions below are open for review
  at the gate.
- **Evidence:** `ucmd-engine/validation/e37-openmm/REPORT.md`.

## Architecture

- **Machine profile `[backend]`** (`kind = "openmm"`, `platform`, `precision`, `device`) plus
  `[executables] ucmd-openmm`. Packages and `run.toml` are unchanged (ADR 0010 §1). The GUI and
  the study driver keep calling `ucmd run`.
- **`ucmd run`** computes the reference single point and execs the bridge:
  - CPU backend, start positions displaced by a seeded 0.01 nm (stream 4);
  - files in `out/backend-reference/`.
- **`ucmd-engine/bridge`** (Python, `ucmd-bridge`):
  - reads the package;
  - builds the OpenMM System, with the engine's PME α and grid set explicitly;
  - checks conformance (1e-6 / 1e-5) and refuses to run otherwise;
  - runs the engine's integrators as CustomIntegrators: velocity Verlet, the Nosé–Hoover chain
    (same Suzuki–Yoshida propagation and masses), Langevin BAOAB, all with full-step velocities;
  - writes thermo, H5MD or XYZ in the spec formats;
  - restarts from its own checkpoint; stops gracefully on SIGINT/SIGTERM.
- **The GPU stack lives in a container** (`bridge/docker`: a ROCm base plus conda-forge OpenMM
  with OpenCL), run by a wrapper script. The host needs no ROCm or OpenCL.

## Deviations from the engine (each recorded in the H5MD provenance)

- **Barostat:** MonteCarloBarostat instead of C-rescale (same ensemble; validated for argon in
  E2.7).
- **Pressure:** the molecular pressure from MonteCarloBarostat.computeCurrentPressure, every
  500 steps (nan in the other thermo rows). OpenMM has no virial.
- **Not available:** CSVR, constraints, anisotropic coupling (all refused).

## Decisions 2026-11-17 (author)

- **Precision:** tiers with statistical admission of mixed precision (ADR 0012); validation in
  `ucmd-engine/validation/e37-precision`.
- **RX 580:** no compute role; the Vega 20 card is the workhorse. Multi-device support stays in
  the software (profile `device`, wrapper `UCMD_OPENMM_DEVICES`), not used on this workstation.
- **Tail correction:** ON (ADR 0009 amendment).

## Questions for the author

1. **Precision:** double passes ADR 0010 at 34 ns/day. Mixed runs at 77 ns/day, but forces
   deviate by 5.5e-5 relative (tolerance 1e-5). Amend ADR 0010 for mixed precision, with a
   statistical-level validation instead, or stay with double?
2. **RX 580:** ROCm 7 does not support it. It needs Mesa's OpenCL (rusticl) on the host, a
   system package (sudo). Install it?
3. **Spec v0.1.1:** document the profile's `[backend]` section (spec/run-config.md §4), together
   with the other pending items (stop exit codes, restart records, XYZ trajectory).

   **Decided 2026-11-28 by agent decisions under the author's delegation: a new version 0.1.4,
   which documents engine behaviour that already exists, after `spec-v0.1.3` is tagged** (ADR
   [0018](../decisions/0018-spec-releases-and-pins.md)).
   - **Not 0.1.1:** 0.1.1 is inside the tag `spec-v0.1.2` (2026-11-25, approved by the author),
     so it is closed.
   - **Not 0.1.3:** 0.1.3's content is approved, implemented in engine `main` and validator 0.1.3,
     and pinned by the engine CI. Adding text to it would make one version name mean two
     contents.
   - **Scope of 0.1.4:** backwards compatible, no new behaviour; every item describes what the
     engine and bridge do now.
     1. The machine profile's `[backend]` table (`kind`, `platform`, `precision`, `device`) and
        `[executables] ucmd-openmm` (run-config.md §4), with the precision tiers of ADR 0012.
     2. Exit status of `ucmd run`:
        - 0 when complete;
        - 128 + signal number after a graceful stop on SIGINT or SIGTERM (130, 143), with a
          checkpoint (`ucmd-cli` main.rs);
        - another non-zero status on an error. After a provider error the engine first writes
          the emergency checkpoint (spec/checkpoint.md, invariant 7).

        The draft must check that the bridge follows the same codes.
     3. The H5MD provenance groups `/parameters/ucmd/restarts` (one group per restart) and
        `/parameters/ucmd/backend` (ADR 0012 §4) in trajectory-h5md.md.
     4. The extended-XYZ trajectory (`.xyz`, Å, one complete frame flushed at a time), as a
        viewing format: positions only. Velocities and forces are refused there (SC-2), and
        analysis reads H5MD.
     5. Editorial: the CHANGELOG headings of 0.1.1 and 0.1.2 still say "not yet tagged".
   - **Not in scope:** a JSON Schema for the machine profile (profiles are never exchanged between
     machines), and live H5MD reading (SWMR). XYZ covers live frames (gate-b2a.md §6 Q4).
   - **Steps:** an agent drafts the text on an umbrella branch and checks each item against the
     engine code. The author approves it and tags it `spec-v0.1.4`. The validator gets
     `SPEC_VERSION = "0.1.4"`; no fixture changes, except an XYZ example if the author wants one.
   - **Reason:** drivers (study driver, queue worker, GUI) already rely on the exit codes, the
     restart records and the XYZ frames. An undocumented contract between components breaks the
     one rule of CLAUDE.md.
   - **What would change it:** if the author wants these items to wait for a larger 0.2 (for
     example with live H5MD), they stay engine behaviour, documented in the engine README until
     then.

# Spec 0.1.2 design — per-pair Lennard-Jones overrides

- **Status:** approved 2026-11-22 (ADR 0015). The author delegated Q1–Q3: "pick the best
  solutions and continue". The proposals were taken, with the reasons in §7.
  - Written at the author's request: "B should not be held up once the clusters are done".
  - This is a spec change (CLAUDE.md, ADR 0008 §3), so **nothing is implemented before the
    author approves it.** The items marked ❓ wait for the author.
  - The decision record is ADR 0015 (proposed).
- **Why:**
  - Trial T6 option B corrects the Li⁺ first shell with its own σ and ε for the pairs
    Li⁺–O(EC carbonyl) and Li⁺–O(EMC carbonyl). All other pairs keep the combination rule.
  - Spec 0.1 cannot express that: LJ pair parameters come only from the atom types through one
    combination rule (system-package.md §5.2).
  - ADR 0008 §3 and §7 foresaw this case. Until the spec has the extension, such terms can only
    run as an external provider.
  - The extension is the standard "NBFIX" form (CHARMM `NBFIX`, GROMACS `[ nonbond_params ]`,
    LAMMPS `pair_coeff i j`). It is also the published route for ion–solvent corrections.
- **Not in scope:**
  - mixing force-field families with different combination rules in one package. With this
    format that is expressible (list every cross pair), but the builder does not do it
    automatically;
  - other functional forms (e.g. 12-6-4).

## 1. Format (system-package.md §5)

```json
"forcefield": {
  "name": "OPLS-AA (…)",
  "combination_rule": "geometric",
  "scale_14_lj": 0.5,
  "scale_14_coulomb": 0.5,
  "atom_types": {"Li.Li": {"sigma_nm": 0.287, "epsilon_kjmol": 0.002092}, "EC.t10": {…}},
  "pair_overrides": [
    {"types": ["Li.Li", "EC.t10"], "sigma_nm": 0.21, "epsilon_kjmol": 0.9,
     "description": "T6 option B (docs/research/trials/T6-…)"}
  ]
}
```

(The numbers are placeholders for the format, not parameters.)

**Rules:**
- `pair_overrides` is optional. Absent or `[]` means exactly the 0.1.0 behaviour.
- **Entries:**
  - `types` holds two keys of `atom_types`. They may be equal (an i–i pair).
  - The pair is unordered: `[a, b]` and `[b, a]` are the same pair.
  - Each pair appears at most once.
  - `sigma_nm` ≥ 0 and `epsilon_kjmol` ≥ 0, as for atom types. `description` is free text.
- **Meaning:** for every pair of atoms with these two types that interacts by LJ (§5.2), σ_ij and
  ε_ij are the override's instead of the combination rule's.
  - That includes 1-4 pairs, which are then scaled by `scale_14_lj` as usual. This is the
    CHARMM behaviour without `NBFIX-14`. ❓ Q2
  - Exclusions are unchanged.
- **Long-range dispersion correction:** the analytic tail correction sums over type pairs. It uses
  the overridden σ_ij and ε_ij for those pairs. Nothing else changes, because the correction
  already works per type pair.
- **Validation (§7):**
  - an override that names an unknown type → `E_REFERENCE` (the rule is extended);
  - a repeated pair → new code `E_PAIR_OVERRIDE`, checked right after `E_REFERENCE`;
  - range violations → `E_SCHEMA`.

## 2. Version

- **0.1.2, backwards compatible:** every 0.1.0 and 0.1.1 file stays valid and means the same.
- **Old readers fail closed.** The schema has `additionalProperties: false` on `forcefield`, and
  the engine reads with `deny_unknown_fields`. A reader without the extension therefore rejects
  such a package with `E_SCHEMA`. It never silently uses the combination rule.
- 0.1.1 (the pressure tensor, approved, not yet tagged) stays as approved. Folding this change
  into it is possible, but would widen an approved scope after the fact. ❓ Q1

## 3. Builder (recipe and provenance)

```toml
[[pair_override]]   # top level (implemented so; was [[forcefield.pair_override]], §8)
types = ["Li.Li", "EC.t10"]   # type names as they appear in the package
sigma_nm = 0.21
epsilon_kjmol = 0.9
citation = "this work, trial T6 option B (docs/research/trials/T6-li-carbonyl-correction.md)"
```

- **Kind of step:** a transform after parameterization, like ζ (ADR 0008 §4).
- **Recording:** it is written to `provenance.transforms` with its values and citation, and the
  citation goes to `provenance.sources`. A missing `citation` is an error (CLAUDE.md: every
  parameter cites a source).
- **Checks:** the build fails if a type is unknown. Type names are the prefixed package names
  (ADR 0009, e.g. `EC.t10`, `Li.Li`).
  They are visible in `system.json`; a command that lists them is part of the work. ❓ Q3
- **Charge scaling (ζ):** it does not touch overrides; they are LJ only.
- **GROMACS import:** reading `[ nonbond_params ]` in the `gromacs-top` source is a separate,
  later step. In GROMACS, generated 1-4 pairs ignore `nonbond_params`, so such an importer must
  refuse an override whose pair also occurs as a 1-4 pair (or the semantics of Q2 change).

## 5. Acceptance tests

- **A1, identity:** overrides equal to the combination rule give the same energy, forces and
  virial as no overrides. Bitwise in the Rust provider (same table entries); ≤ 1e-12 relative in
  the bridge and the oracle.
- **A2, oracle:** on the new fixture, the Rust provider against the OpenMM oracle (energy,
  forces, virial), at the existing E2 tolerances. The fixture has two types, one override,
  periodic, and runs with the tail correction on and off and with the cutoff modes `truncate`
  and `shift`.
- **A3, finite differences:** the force check with overrides, like the existing LJ tests.
- **A4, tail correction:** the analytic correction of a two-type system with an override, against
  the formula evaluated by hand.
- **A5, 1-4:** a molecule in which an overridden pair is 1-4. It is scaled by `scale_14_lj`;
  compared with the oracle.
- **A6, validator:** the valid fixture passes; the invalid ones fail with their codes; all 0.1.0
  fixtures are unchanged.
- **A7, bridge against engine:** a short NVE run on a small Li⁺/EC/EMC box with overrides. The
  per-step energies agree within the existing E3.7 tolerance.
- **A8, fail closed:** a reader built from the current main rejects the 0.1.2 fixture (one test
  against the 0.1.1 schema).
- **A9, T6 link:** t6_fit's option B values, written as a package through the builder, reproduce
  t6_fit's own energies on all five clusters to 1e-9 kJ/mol.

## 6. Cost and order

- **Work:** about one working day, one PR per repo, in this order: spec + validator → oracle →
  Rust → bridge → builder.
- **Timing:** that is the time the T6 clusters take on the CPU. If approved now, option B's
  liquid runs can start as soon as stage 2 has its values.

## 7. Questions, decided 2026-11-22 (delegated by the author)

- **Q1:** 0.1.2 as its own version (proposed), or folded into the untagged 0.1.1?
  **Decided: 0.1.2.** 0.1.1 keeps the scope it was approved with.
- **Q2:** 1-4 pairs: should overrides apply to them too (proposed: one rule everywhere, CHARMM
  behaviour), or should 1-4 keep the combination rule (GROMACS behaviour)? For T6 it makes no
  difference: Li⁺ has no 1-4 pairs.
  **Decided: everywhere.** One rule without hidden cases, as in CHARMM, LAMMPS and OpenMM's
  CHARMM reader. A GROMACS importer must refuse the cases where GROMACS differs (§3).
- **Q3:** in recipes, are overrides selected by the package type name (proposed), or by molecule
  and atom name in the template?
  **Decided: type names.** They are unique and appear verbatim in the package, so the recipe and
  the package say the same thing.

**Deviations from §3–§5:**
- **Recipe key:** it is top level, `[[pair_override]]`, not `[[forcefield.pair_override]]`.
  - `[forcefield]` holds the options of a source, and components can carry their own
    `[component.forcefield]`.
  - An override is a package-level transform and belongs to neither.
- **A5** compares with the analytic LJ of the pair, not with the oracle. The value is exact, so
  the check is not weaker.
- **A7** checks the conformance single point of a 20-step run on kob-andersen-500, not a
  Li⁺/EC/EMC box, and without the tail correction (the finding below).
- **A9** writes the overrides into the T6 package directly, not through a builder recipe, so it
  needs no packing. The builder's writing of overrides is tested separately in
  `test_build.py`.
- **Not done:** the GUI does not show overrides yet; recipes keep them through the GUI's
  round-trip (tested). There is no listing command for type names; the build error lists the
  package's type names instead.

**Finding: the tail correction in the bridge for several atom types.** This is independent of
overrides and predates them.
- OpenMM's `CustomNonbondedForce` long-range correction counts n_a(n_a + 1)/2 pairs within a
  type class and n_a n_b across classes, then rescales the total to N²/2. The engine and the
  analytic formula count N_a N_b.
- The two agree for one type and differ by O(1/N) otherwise: 1.3e-5 of the total energy for
  kob-andersen-500, against a conformance tolerance of 1e-6.
- In the 1 M electrolyte the total energy is dominated by Coulomb, so the relative difference is
  far smaller. T2's conformance checks passed; it was not measured separately.
- Correcting it in the bridge means replacing OpenMM's correction with the engine's formula (a
  V-dependent energy term). That is a separate change; until then kob-andersen-500 runs on the
  bridge without the tail.
